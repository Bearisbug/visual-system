# visual-system · 规则治理

仅维护本 Skill 时使用。规则、库数据、品牌项目产物分开；运行时与用户要求优先于本约定。

## 文件与唯一出处

- `SKILL.md`：适用范围与阶段路由，不复制规则正文。
- `00-catalog.md`：每卡一行，ID、触发和唯一文件锚点。
- `runtime.md`：按产物选择运行能力与跨 Agent 接续。
- `design.md`：输入、来源、构思、反馈与材质；`assets.md`：字体、母版、导出与交付；`system.md`：品牌语言、设计系统 token、图标与应用；`handoff.md`：开发视觉交接。
- `flow-*.md`：顺序流程，通过 ID 引用规则，不另定义同一要求。
- `specimen-spec.md`：外部的标准组件样例页规格，完整深度的 tokens 须满足它；规则卡引用它，不在其中定义规则。
- `validation-contract.md`：机械数据合同；`libraries/`：按各库索引定义的资源数据。
- `vendor/<上游>/`：上游原样副本，`SOURCE.json` 登记提交号与逐文件 SHA-256；只能整体替换为上游新提交，不在本仓修改。

规则头为 `## BD-<类别>-<三位序号> · <标题>`，紧前一行写小写显式锚点，例如 `<a id="bd-input-001"></a>`。ID 在整个 Skill 唯一，类别内递增，不复用被删除 ID。每卡字段为“触发、规则、产物、验证”；必要时补“边界”。规则用可执行的必须、默认、先、再、只有当表述。触发写成可判定条件（用户原话、手里的输入物、所处阶段），不写「涉及 X 时」这类泛指；一卡一事，卡里出现两个互不依赖的触发时拆成两张卡。外部来源的整理与本库推导需分开。

同一约束只在一张卡定义。入口、流程和库中的相关说明引用 ID；数据记录不因为新增样本而创建规则卡。任何执行依赖留在 Skill 内，可选外部工具必须声明用途与缺失时的边界。

## 增改与验证

1. 先检索 catalog 和既有文件，判断是否已有同义规则；读取 Harness 优化档案的拒因和回归记录。
2. 按证据更新唯一出处、catalog 与调用者；字段含义变化同时检查旧数据和校验器，禁止静默误读。
3. 一个内容文件只收一个子主题，判据是文件里的全部卡能否用一句话概括成同一子主题；新卡的触发处境落在现有子主题之外时拆出新文件，保持 ID。catalog 保持单一总入口。不为形式拆空文件。
4. 运行 `check.sh`；新增或修改脚本用合规和不合规输入真跑。机械、行为和视觉结果分别登记。
5. 规则卡变更执行仓库优化循环：盲测→反思→有界修改→相关回归。每轮修改预算与拒因处理遵循仓库 AGENTS。测试写 Harness 的 `skill-tests/visual-system/` 与 `evals/visual-system.md`，不成为发布时的外部运行依赖。

发布文件只陈述当前规则。修订过程、失败、未采用方向和教训进入优化档案。只有有对应任务、输入、产物、版本和评审证据时，才能提升能力或库条目的验证状态。
